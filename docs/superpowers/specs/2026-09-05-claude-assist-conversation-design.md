# Claude Assist Conversation Agent — Design

Date: 2026-09-05
Status: Approved for planning

## 1. Goal

Let Home Assistant's **Assist** talk to Claude. A custom integration exposes one
or more `conversation` entities; each routes a turn through `claude -p` running
inside this add-on, with the model selectable per agent.

Assist is the point. Voice and the chat panel are the intended front ends.

## 2. Why this shape

A HA custom integration runs inside the **HA Core container**, which has no
`claude` binary and never will. The integration therefore cannot spawn `claude
-p` itself — it must call something in the add-on container over HTTP.

That single constraint produces the whole architecture: a thin prompt API in the
add-on, and a conversation entity that is an HTTP client of it.

## 3. Architecture

```
Assist pipeline                                          [HA Core container]
  conversation.claude_<name>  (ConversationEntity)
        |  POST /conversation   (bearer token, hassio network)
        v
  prompt-api :8098  (s6 service)                         [add-on container]
        |  spawn: claude -p --output-format json ...
        v
  claude  --MCP(http)-->  http://homeassistant:8123/api/mcp/assist
                                                         [back into HA Core]
```

The request loops back into HA. That is intentional: HA builds the system prompt
(including the exposed-entity list) and hands it over; Claude then acts through
HA's own Assist intents, scoped to the same entities Assist exposes.

Two consequences worth stating plainly:

- The tool-calling loop lives **inside** `claude -p`. HA sees one request and
  one final text answer. Where `ollama`/`open_router` run a
  `for _ in range(MAX_TOOL_ITERATIONS)` loop in `entity.py`, ours does not.
- `CONF_LLM_HASS_API` is used only to *generate the prompt*, never to execute
  tools. See §6.

## 4. Prior art

Read from `home-assistant/core@dev`: `ollama`, `open_router`, `anthropic`. They
share one template, which this design follows:

- Config entry = the connection. Conversation agents are **subentries** of type
  `"conversation"` holding `CONF_MODEL` / `CONF_PROMPT` / `CONF_LLM_HASS_API`.
  `async_get_supported_subentry_types()` wires the subentry flow.
- `_async_handle_message` is seven lines in all three: call
  `chat_log.async_provide_llm_data(...)`, call `_async_handle_chat_log(...)`,
  return `conversation.async_get_result_from_chat_log(user_input, chat_log)`.
- File layout: `manifest.json`, `__init__.py`, `entity.py`, `conversation.py`,
  `config_flow.py`, `const.py`, `strings.json`.

The subentry model is what makes "configurable model" fall out naturally: N
agents on one connection, each its own model, device and entity, each separately
selectable in an Assist pipeline.

## 5. Components

### 5.1 `app/prompt-api.js` (add-on)

Node, no new dependencies — `http`, `child_process`, `crypto`.

`GET /health` -> `{ok, claude_version}`. Used by config-flow validation and by
`async_setup_entry` (failure raises `ConfigEntryNotReady`). The model list is a
constant in the integration (§6), not served here — it changes with Claude Code
releases, not with this add-on.

`POST /conversation`
- request: `{text, conversation_id, model, system_prompt}`
- response: `{text, session_id, duration_ms, cost_usd, is_error}`
- auth: `Authorization: Bearer <token>`, token read from `/data/prompt-api-token`,
  generated by `30-deploy-integration.sh` on first run. Missing or wrong -> 401.

The listener binds port 8098 on the Supervisor network only. `config.yaml` gains
no `ports:` mapping, so it is reachable from HA Core and from nothing else.

Invocation:

```
claude -p "<text>"
  --output-format json
  --model <model>
  --session-id <uuid>     # first turn of a conversation
  --resume <uuid>         # subsequent turns
  --system-prompt "<HA-generated prompt>"
  --system-prompt-snapshot on
  --mcp-config /data/.claude/mcp-assist.json
  --strict-mcp-config
  --tools ""
  --permission-mode bypassPermissions
  --setting-sources ""
  --disable-slash-commands
  --max-budget-usd <cap>
```

`--tools ""` disables every built-in tool, so with `--strict-mcp-config` the
session's entire capability is the HA Assist MCP. There is no allow/deny list to
keep in sync as Claude Code adds tools — the surface is closed by default.

Session continuity: HA's `conversation_id` (a ULID) maps to a deterministic
UUIDv5 under a fixed namespace. Turn one passes `--session-id`; later turns pass
`--resume`. If `--resume` fails because the session file is gone (add-on
restart, `/data` cleared), retry once with `--session-id` — the turn degrades to
no-history rather than erroring. Sessions run with a fixed `cwd`
(`/data/assist-workspace`) because Claude scopes session storage by project
directory.

Process hygiene: hard timeout (default 60 s) killing the whole process group; a
concurrency cap (default 2) returning 503 past it, because each `claude` is
heavy and HA hardware is not.

### 5.2 `rootfs/etc/services.d/prompt-api/run`

s6 service alongside the existing `claude` and `ttyd` services.

### 5.3 `rootfs/etc/cont-init.d/20-mcp-assist.sh`

Writes `/data/.claude/mcp-assist.json` pointing at HA's MCP server.

Auth is a spike: `/api/mcp/assist` sits under `/api/`, so the add-on's existing
`SUPERVISOR_TOKEN` (it already declares `homeassistant_api: true`) may work
directly and need no setup at all on HAOS. Verify with a real request; if it
fails, fall back to a long-lived access token supplied as an add-on option, and
fail loudly with instructions rather than silently degrading.

Deliberately a **separate file** from the existing `mcp.json`: the Assist agent
gets HA-native intents only, while the interactive Remote Control session keeps
the full vibecode-agent surface. Neither inherits the other's tools.

### 5.4 `rootfs/etc/cont-init.d/30-deploy-integration.sh`

The add-on already maps `homeassistant_config:rw`. On init it copies
`custom_components/claude_code_conversation/` into the HA config dir, but only
when the deployed version differs from the shipped one. Beside it, writes
`.addon.json` = `{base_url, token}` — the add-on knows its own Supervisor
hostname, which the integration cannot guess (repo-hash prefixed). Logs a clear
"restart Home Assistant to load this".

This keeps the integration version and the prompt-API contract locked together.
No HACS step, and no version skew between the two halves.

### 5.5 `custom_components/claude_code_conversation/`

Mirrors the ollama layout. `manifest.json` declares
`dependencies: ["conversation"]`, `after_dependencies: ["assist_pipeline",
"intent"]`, `integration_type: "service"`, `single_config_entry: true`.

`entity.py::_async_handle_chat_log` is one HTTP call followed by
`chat_log.async_add_assistant_content_without_tools(...)`.

## 6. Configuration surface

**Config entry (exactly one)** — `base_url`, `token`. The flow pre-fills both
from `.addon.json`, so the normal path is clicking Submit. Validated against
`GET /health`. `runtime_data` holds a `PromptApiClient` over HA's shared aiohttp
session.

**Conversation subentry (N)**

| Field | Selector | Default |
|---|---|---|
| `CONF_MODEL` | dropdown `opus`/`sonnet`/`haiku`/`fable`, `custom_value=True` | `sonnet` |
| `CONF_NAME` | text | the model name |
| `CONF_PROMPT` | `TemplateSelector` | `llm.DEFAULT_INSTRUCTIONS_PROMPT` |

`custom_value=True` lets a pinned id (`claude-opus-5`) be typed in.

`CONF_LLM_HASS_API` is pinned to `[llm.LLM_API_ASSIST]` and **not shown in the
form**. It is load-bearing — it is what makes `async_provide_llm_data` emit the
exposed-entity list — but here it never causes HA to execute a tool; Claude does
that over MCP. A visible toggle that means something different from what the
identical toggle means in every other HA integration is worse than no toggle.

Each subentry gets its own device (`DeviceEntryType.SERVICE`, manufacturer
`Anthropic`, model = the alias, `sw_version` = the Claude version from
`/health`) and `ConversationEntityFeature.CONTROL`.

Timeout, entity-injection and permission mode are **not** user-configurable.
They are fixed at safe values; adding knobs is a later change if real use
demands it.

## 7. Error handling

All failures raise `HomeAssistantError` with a `translation_key` so Assist
speaks something actionable:

| Condition | Behaviour |
|---|---|
| `/health` fails at setup | `ConfigEntryNotReady` — HA retries with backoff |
| add-on unreachable / 5xx | "the Claude add-on isn't responding" |
| 503 from concurrency cap | "busy, try again in a moment" |
| timeout | its own message, distinct from unreachable — the fixes differ |
| `claude` returns `is_error: true` | surface its `result` text **as the spoken answer**, not an exception; it is usually a real answer ("I can't see that entity") |
| image attachment present | explicit unsupported-attachment error |

## 8. Scope

**In:** text conversations through Assist; per-agent model selection; per-agent
system prompt; session continuity within a conversation; add-on-side deployment
and discovery of the integration.

**Out (v1), with reasons:**
- **Streaming** — `_attr_supports_streaming = False`. `--output-format
  stream-json` behind SSE is a later change the HTTP contract already permits.
- **`Platform.AI_TASK`** — the reference integrations ship it; Assist was the
  ask.
- **HACS packaging** — the add-on deploys the integration.
- **Image attachments** — text only.
- **Warm process pool** — considered and rejected for v1 (see §9).

## 9. Rejected alternatives

**Warm `claude` process pool** (`--input-format stream-json`) removes the
~1-3 s per-turn cold start, but the add-on then owns pool eviction,
per-conversation affinity and stuck-process detection, and a wedged process
poisons a conversation silently. The cold start is small next to the MCP tool
round-trips a controlling turn pays anyway. It is a drop-in replacement behind
the same HTTP contract if real latency proves otherwise — the integration would
not change.

**File-drop IPC** through the shared config dir avoids ports and auth entirely,
but means polling latency, litter in the user's config directory, and no natural
timeout or backpressure story.

**Third-party `@coolver/home-assistant-mcp` for Assist** is far more capable —
it can write automations and edit YAML — but ignores Assist exposure settings,
so a misheard voice command reaches the whole install. It stays on the
interactive session, where a human is watching.

**HA-side tool execution** (`llm_hass_api` tools executed by `entity.py`, as
ollama does) needs a mid-turn round trip back into HA, which a one-shot
`claude -p` cannot do.

## 10. Testing

**Node** — `node --test`, no new dependencies. A fake `claude` on `PATH`
emitting a canned JSON envelope. Covers: argv construction per model,
`--session-id` on turn one vs `--resume` after, the resume-failure fallback,
timeout killing the process group, 503 past the concurrency cap, 401 on a bad
token.

**Python** — `pytest-homeassistant-custom-component` + `aioresponses`. Covers:
config flow success and `cannot_connect`, `.addon.json` pre-fill, subentry
create and reconfigure, conversation happy path, timeout, `is_error`
passthrough, attachment rejection, plus entity and device registry snapshots as
HA core does.

**Manual end-to-end**, once: enable the MCP Server integration, restart HA,
create a `sonnet` agent, point a pipeline at it, then ask *"which lights are on
in the living room?"* followed by *"turn them off"*. The second question only
works if session resume is wired correctly, so it exercises the part unit tests
cannot.

## 11. Open questions for implementation

1. Does `/api/mcp/assist` accept `SUPERVISOR_TOKEN`? Spike first; long-lived
   token is the documented fallback (§5.3).
2. Does the Supervisor core proxy pass MCP streaming cleanly, or must the add-on
   reach `http://homeassistant:8123` directly?
3. Actual per-turn latency on real HA hardware with a `haiku` agent — decides
   whether §9's warm pool gets promoted from rejected to planned.
